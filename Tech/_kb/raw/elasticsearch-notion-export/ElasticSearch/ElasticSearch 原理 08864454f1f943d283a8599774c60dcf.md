# ElasticSearch 原理

- 全文检索实现原理
    
    全文检索是基于分词和倒排索引实现。
    
    - 分词：对文档内容进行分析转化为一系列单词或词组（term/token）的过程
        - 分词器（Analyzer）：分词器是分词在技术层面上的具体实现，ElasticSearch 提供了多种分词器实现不同规则的分词的操作。默认分词器为 Standard Analyzer，它按词切分，进行英文单词进行小写处理。同时 ElasticSearch 也支持实现自定义分词器。
    - 倒排索引：根据分词结果构建倒排索引，倒排索引是一种索引数据结构，它将文档中的词元映射到包含该词元所在的文档列表以及在文档中的词频（用于评分）和位置，实现快速定位包含指定词元的文档。

- 基于相关性算法实现的排序
    
    在实现对搜索结果的排序时，ElasticSearch 通过 相关性算法 计算查询条件与匹配文档之间的相关性分数，根据相关性分数的分值进行排序。相关性分数的分值描述了 查询文档 和 查询条件 的匹配程度，分值越高，则说明文档越符合预期，排名越靠前。
    
    常见算法：
    
    - BM25 算法：ElasticSearch 5.x后默认使用的算法，它是一种基于概率的信息检索算法，通过考虑查询词在文档中的频率、文档的长度以及整个语料库中的文档频率来计算查询与文档之间的相关性分数。
    - TF-IDF 算法（`Term Frequency-Inverse Document Frequency`）：TF-IDF 算法通过 词项频率（TF）和 逆文档频率（IDF）来评估一个词在文档中的重要性。
    
    TF-IDF 算法会随着词频的增加而越来越大，而BM25 算法会随着词频的增加而增常曲线趋于平缓。

- 集群分布式底层实现和原理
    
    ElasticSearch 是一个分布式搜索引擎，支持自动基于分片将索引数据分散到不同的节点上。
    
    - 文档写入原理
        
        ![Untitled](ElasticSearch%20%E5%8E%9F%E7%90%86/Untitled%201.png)
        
        - 协调节点：客户端向 ElasticSearch 发送一个文档写入请求到 ElasticSearch 的任一节点，该节点临时充当协调节点（Coordinate Node），协调节点的主要职责是将请求路由到正确的主分片的所在节点上。
        - 路由分片：协调节点根据 文档ID 计算哈希值，然后对其用主分片 shard 数进行取模，余数就是 该文档实际存储的主分片的位置，以保证数据均衡。（注意：**协调算法与分片数量有关，因此索引库一旦创建，主分片数量不能改变**）
            
            ![Untitled](ElasticSearch%20%E5%8E%9F%E7%90%86/Untitled%202.png)
            
        - 写入主分片并复制到副本分片：协调节点将文档写入请求路由到正确的主分片的所在节点上，该节点执行写入操作并确认成功后，将数据同步复制到对应的副本分片节点。
        - 返回响应：当所有的副本分片确认写入成功后，文档主分片节点将响应返回给协调节点，协调节点将最终的响应返回给客户端。
            
            ```json
            GET /my_index/_search
            {
              "explain": true,    // 添加此参数可以看到文档数据具体所在分片
              "query": {
                "match_all": {}
              }
            }
            ```
            
    - 文档提取原理
        
        ![Untitled](ElasticSearch%20%E5%8E%9F%E7%90%86/Untitled%203.png)
        
        - 协调节点：客户端发送文档提取请求（根据文档ID查询文档）到协调节点上。
        - 路由分片：协调节点根据文档ID进行哈希运算，确定文档实际存储的主分片的节点位置。
        - 负载读取：协调节点将请求负载路由到主分片和其对应的副本分片上，实现读请求的负载，实际路由到的分片被称为目标分片。
        - 返回响应：目标分片执行读取并返回文档数据到协调节点，协调节点将结果返回给客户端。
    - 文档搜索原理
        
        ElasticSearch 集群搜索整体分为两个阶段：分散阶段（Scatter phase）、 聚集阶段（Gather phase）和 回查阶段（Fetch phase）。
        
        - 分散阶段：协调节点接收客户端搜索请求后，它根据索引分片信息将请求分发到集群中的各个相关分片所在的数据节点上（每个索引分片有一个或多个主分片和一个或多个副本分片，搜索请求会发送到这些分片中的一个）；每个数据节点接收到搜索请求后，对本地分片执行搜索操作，返回给协调节点包括匹配的文档ID和相应的评分的中间结果列表（Top-K 文档ID列表）。
        - 聚集阶段：协调节点汇总各个数据节点返回的局部的中间结果列表，对中间结果列表进行合并和排序，确定全局的中间结果列表。
        - 回查阶段：协调节点根据文档ID列表向相应的分片所在节点请求完整的文档内容，生成最终的搜索文档结果列表并返回给客户端。
        
        ![Untitled](ElasticSearch%20%E5%8E%9F%E7%90%86/Untitled%204.png)
        
        ![Untitled](ElasticSearch%20%E5%8E%9F%E7%90%86/Untitled%205.png)
        
        详细过程如下：
        
        - 协调节点：客户端发送文档搜索请求到协调节点上。
        - 广播请求到所有分片：协调节点将搜索请求广播到所有与该索引相关的分片的所在数据节点上。
        - 分片级别查询：每个分片独立执行搜索操作，通过倒排索引查找匹配的文档并计算文档评分，每个分片返回协调节点一个包含文档ID和评分的中间结果列表。
        - 处理结果：各分片将各自分片的中间结果列表返回到协调节点，协调节点对所有的中间结果列表进行合并、排序和分页等处理，获取最终的中间结果列表。
        - 文档提取：协调节点根据结果列表，通过文档ID从对应的分片请求完整的文档内容。
        - 返回响应：协调节点将最终的搜索文档结果返回给客户端。
- 文档写入底层原理
    
    ![Untitled](ElasticSearch%20%E5%8E%9F%E7%90%86/Untitled%206.png)
    
    - 写入内存索引缓冲区（index buffer）
        - 文档将先被写入内存缓冲区（索引缓冲区），该缓冲区在 ElasticSearch 应用的 JVM 堆内存中，用于临时存储新创建的文档，处于内存缓冲区的文档是对搜索不可见的。
    - 记录操作日志 - translog
        - 写入索引缓冲区的同时，文档操作也会被记录到操作日志中。
            
            translog：一个追加写入的日志文件，记录自上次刷盘的所有操作。
            
            translog 日志的作用：当系统崩溃或重启时，translog 用于重放操作恢复尚未刷新（flush）到磁盘的操作，防止数据丢失，保证数据的持久性。
            
    - 刷新文件系统的高速缓存区（filesystem cache）- refresh
        - index buffer 缓冲区中的文档数据将会在默认每隔一秒，将缓冲区的 refresh 刷新到操作系统的文件系统缓冲区中的段文件（segment），处于操作系统的文件系统缓冲区的文档是对搜索可见的。
            
            段文件（segment）是 Lucene 索引的基础结构，包含倒排索引、存储字段、词典等数据结构。它是不可变的文件，数据加入索引会不断创建新的段文件。
            
    - 段（segment）刷新磁盘（disk） - flush
        - 默认每隔30分钟，文件系统的高速缓存区的索引数据将会被强制持久化 flush 到磁盘中即刷盘。
        - flush 刷盘成功后，ElasticSearch 会截断 translog，删除已经被刷新到段文件中的操作记录。
    - ElasticSearch 准实时性 NRT
        
        ElasticSearch 是准实时性（Near real-time, NRT）的，它指数据加入索引和数据对搜索可见之间存在短暂的延迟。延迟的时间是刷新间隔时间（Refresh interval），默认为 1 秒，可以通过 index.refresh_interval  参数来调整 refresh 的时间间隔。
        
        refresh 是指将数据从 ElasticSearch 内存缓冲区 刷新到 操作系统的文件系统缓存区 中，处于ElasticSearch 内存缓冲区的索引数据对搜索是不可见的，处于操作系统的文件系统缓存区的索引数据对于搜索是可见的。 
        
    - ElasticSearch 数据丢失问题
        
        ElasticSearch 通过 translog 操作日志一定程度上降低了数据丢失的风险，当系统崩溃或重启时，translog 用于重放操作恢复尚未刷新（flush）到磁盘的操作，重放时会将 translog 中的数据先写入到 缓存 和 操作系统文件缓冲区中，默认5秒将缓冲区的数据 flush 到磁盘中，在这5秒内，如果服务故障或宕机，会导致最多5秒的数据丢失。
        
    - ElasticSearch 更新和删除文档原理
        - 删除操作：当删除文档时，ElasticSearch 不会立即将文档从磁盘中移除，而是将文档标记为逻辑删除。
            - ElasticSearch 通过 .del 文件记录被标记为删除状态的文档，当文档被删除时，ElasticSearch 会在文档的元数据中将其标记为 已删除，并在其倒排索引中更新删除标识，再将其记录到 .del 文件中。
        - 更新操作（先逻辑删除后新增）：当更新文档时，ElasticSearch 先将文档标记为删除状态，然后重新创建一个更新后的文档写入到分片中。
    - ElasticSearch segment merge 段合并
        
        > 段文件（segment）是 Lucene 索引的基础结构，包含倒排索引、存储字段、词典等数据结构。它是不可变的文件，数据加入索引会不断创建新的段文件。为了优化搜索性能和IO性能以及管理删除状态的文档，ElasticSearch 通过定期段合并（segment merge）的方式进行优化和解决。
        > 
        
        当 segment 文件过多过大时，可以将多个小的 segment 合并为一个大的 segment，此过程时异步执行的，执行的过程不会影响索引数据的可见性。在合并的过程中，ElasticSearch 将跳过已经标记为删除状态文档，新的 segment 段文件将代替旧的 segment 段文件，旧的 segment 段文件将会被删除，释放磁盘空间。
